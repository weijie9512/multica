## 1. `working_dir` field on projects

**Commit subject:** `customize: add working_dir field to projects`
**Issue this solves:** Multica's daemon hardcodes the spawn directory to `{MULTICA_WORKSPACES_ROOT}/{workspace_id}/{task_id_short}/workdir/` (see `server/internal/daemon/execenv/execenv.go:68–94`). For a single-developer setup where projects map to real git repos on the host, I want the agent to spawn directly inside the repo so it can see my real files and real git state — not an isolated scratch directory.

**Scope:** Add a nullable `working_dir TEXT` column to the `project` table. When set, the daemon spawns the agent (Claude Code / Codex) with `cwd = project.working_dir` for every task attached to an issue in that project. When null, existing behavior is preserved (isolated directory under `MULTICA_WORKSPACES_ROOT`).

**Key implementation trick:** Instead of adding a new field to the daemon claim response and touching `execenv` internals, the change piggybacks on the existing `PriorWorkDir` mechanism. The claim handler (`server/internal/handler/daemon.go:ClaimTaskByRuntime`) hijacks `resp.PriorWorkDir` with `project.working_dir` when set, and the daemon's existing `execenv.Reuse()` code path (`server/internal/daemon/daemon.go:904–907`) picks up the override with zero daemon-internal changes. This cut the diff from ~10 files to ~8 hand-edited files.

**Priority rule:** `project.working_dir` always wins over the historical `prior_session.work_dir`. An explicit project config beats a stale reused path.

**Fallback behavior:**
- Issue has no `project_id` → default behavior (isolated under `WORKSPACES_ROOT`)
- Project has `working_dir = NULL` → default behavior
- `working_dir` is set but the path doesn't exist on the host → `execenv.Reuse()` returns nil and the daemon silently falls back to `Prepare()` which creates the isolated directory. No loud error. A future hardening pass could surface this as a task failure with a clear message.

## 2. Wiki metadata gates on issues

**Commit history:**
- `b41e0ad5 customize: add wiki metadata fields to issues` (2026-04-11) — original, added 3 columns + UI for the Phase 5 polling sidecar
- `3a96beb6 customize: expose wiki fields in issue list responses` (2026-04-11) — enable Phase 5 sidecar to see the fields in list queries
- **`<042 commit> customize: drop wiki_query_hint column`** (2026-04-12) — removed the hint field; see "Current state" below

**Issue this solves:** Agents should only consult or write to the memex knowledge base on issues the user explicitly opts into. Without per-issue gates, you'd either enrich every task (noisy, confusing) or none of them (defeats the purpose).

### Current state (after migration 042)

Two boolean columns on the `issue` table:

| Column | Type | Default | Purpose |
|---|---|---|---|
| `consult_wiki` | `BOOLEAN NOT NULL` | `FALSE` | When true, the daemon's meta skill tells the agent to use the `memex` skill to pull prior context before starting work |
| `allow_wiki_writes` | `BOOLEAN NOT NULL` | `FALSE` | When true, the daemon's meta skill tells the agent to use the `memex` skill to save a summary before marking the task done |

Both opt-in. Both surfaced to the agent via the runtime config meta skill generated per task — see Customization #3 for that wiring.

### How this replaced the polling sidecar

The original commit `b41e0ad5` added a third field, `wiki_query_hint`, and the launcher ran a TypeScript polling sidecar that read all three fields, called memex's HTTP API, and posted marker comments on flagged issues.

In 2026-04-12 the launcher retired the sidecar and moved to an on-demand model: agents carry a `memex` skill (installed via Multica's skills UI) and call memex themselves when the per-task meta skill indicates they should. The hint field became redundant — the agent formulates its own query from the issue title and description. Migration 042 dropped the column; Customization #3 wires the two remaining booleans into the per-task meta skill.

See `../../memex/INSTRUCTION.md` for the skill body the user pastes into the Multica UI and `../../PROJECT.md` Phase 8 for the full cleanup.

### Implementation notes

- **Update handler uses `pgtype.Bool` for nullable-in-update.** The sqlc `UPDATE` query uses `COALESCE(sqlc.narg('consult_wiki'), consult_wiki)` so omitting the field in a PATCH preserves the previous value. Generated `UpdateIssueParams` types the bool as `pgtype.Bool` even though the column is `NOT NULL` — this is correct; the nullability is "present-in-update" not "present-in-db".
- **Create handler defaults.** `CreateIssueRequest` treats both booleans as `*bool`: missing → false, explicit false → false, explicit true → true.
- **No daemon changes in THIS customization.** The daemon-side prompt injection that reads the two flags lives in Customization #3 — see that section for the runtime config meta-skill wiring.

## 3. Memex integration hints in the agent's task prompt

**Commit history:**
- `customize: inject memex integration hints into agent runtime config` (original — rendered hints in `CLAUDE.md` via `buildMetaSkillContent`)
- `customize: move memex hints from CLAUDE.md to task prompt` — moved the conditional section into `BuildPrompt` so hints are per-task and ephemeral, not persisted in a file that survives workdir reuse

**Issue this solves:** Customization #2 added two boolean gates on the issue table (`consult_wiki`, `allow_wiki_writes`) that tell whether a task should use the launcher's memex knowledge service. After retiring the polling sidecar (launcher Phase 8), the only thing that can *act* on those gates is the agent itself via the `memex` skill. But the skill is workspace-wide — the agent needs a per-task signal to know whether to invoke it for *this* particular task. This customization wires the two flags through the daemon's task-claim path and into the task prompt passed to `backend.Execute`.

**Scope:** Thread two booleans from the `issue` row → claim response → daemon task → `BuildPrompt`, which emits a conditional `## Memex integration` section in the prompt string. When both flags are false, the section is absent and the prompt is identical to vanilla Multica.

### Why the prompt and not CLAUDE.md

The original implementation rendered memex hints into `CLAUDE.md` / `AGENTS.md` via `buildMetaSkillContent`. This was wrong because:

1. **Workdirs are reused** across tasks on the same `(agent, issue)` pair. A `CLAUDE.md` written for issue A (with `consult_wiki=true`) would persist and mislead the agent on issue B (with `consult_wiki=false`) if they share the same project working directory.
2. **Different issues in the same project can have different flags.** The meta skill file is project-scoped; the flags are issue-scoped.
3. **`CLAUDE.md` may already exist** in real project repos. Overwriting it clobbers the project's own instructions.

The task prompt is ephemeral and per-task — the right place for per-issue state. The memex section is ~3 lines, so the prompt cost is negligible.

### Data flow

```
issue.consult_wiki / allow_wiki_writes   (db row)
        │
        ▼  GetIssue inside ClaimTaskByRuntime
AgentTaskResponse.ConsultWiki / AllowWikiWrites   (server/internal/handler/agent.go)
        │
        ▼  JSON over /daemon/claim-task
Task.ConsultWiki / AllowWikiWrites   (server/internal/daemon/types.go)
        │
        ▼  BuildPrompt
prompt string → backend.Execute   (ephemeral, per-task)
```

Nothing else reads the two flags on the daemon side. Removing this customization leaves vanilla behavior intact.

## 4. Branch/PR metadata on issues (schema + API + UI)

**Issue this solves:** When agents work on coding tasks, there's no visibility into what branch they're on or whether a PR was created. Users have to check GitHub manually. This customization adds `branch_name` and `pr_url` columns to the issue table and renders them as badges on board cards and in the issue detail properties panel.

**Scope:** Nullable `branch_name TEXT` and `pr_url TEXT` columns on the `issue` table. Populated by the daemon on task completion (via `UpdateIssueBranchPR` query called from the `CompleteTask` handler). Rendered conditionally on the board card as either a branch pill (muted, with git-branch icon) or a PR link badge (purple, clickable, with PR icon). PR badge replaces branch pill when both are set.

## 5. Daemon worktree isolation + PR detection

**Issue this solves:** Customization #1 (`working_dir`) spawns agents directly in the user's repo checkout. This risks destructive changes on the user's current branch. Agents should work on isolated branches via git worktrees, and the system should detect PRs they create.

**Scope:** Automatically create a git worktree when the daemon spawns an agent on a project with `working_dir`. Supports both local paths (creates worktree from the local repo) and remote URLs (uses `repocache.CreateWorktree`). After the agent finishes, detects any PR opened via `gh pr list` and reports both `branch_name` and `pr_url` through the task completion flow. The agent's prompt tells it which branch it's on and to push + open a draft PR.

**Data flow:**

```
working_dir (local path or remote URL)
  → daemon detects type
  → local: setupGitWorktree from local repo
  → remote: repoCache.Sync + CreateWorktree from bare cache
  → agent spawns in worktree on branch agent/{name}/{shortID}
  → prompt: "You are on branch X, push and open draft PR"
  → agent finishes
  → DetectPR via `gh pr list --head <branch>`
  → CompleteTask sends branch_name + pr_url
  → server persists on issue (Customization #4)
```
